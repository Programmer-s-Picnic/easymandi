# Easy Mandi — Android distribution and Google Play release

## Verified APK download locations

These **APK files are for direct Android installation**, not for uploading to Play Console. The three fixed URLs are served from the Easy Mandi GitHub Pages repository and are copied only from builds verified by `apk/release-config.json` and SHA-256 checksum manifests.

- Customer arm64: https://easymandi.in/apk/easymani64.apk
- Customer armeabi-v7a: https://easymandi.in/apk/easymani32.apk
- Delivery partner: https://easymandi.in/apk/easymanideliverypartner.apk

See `apk/build.json` and `apk/SHA256SUMS` for the pinned versions and binary checksums. To update the three fixed URLs in future, publish verified source APKs to the original distribution repositories, update `apk/release-config.json`, and let the `Publish verified APKs to easymandi.in/apk` workflow validate and copy them. Do **not** manually rename arbitrary APKs.

## Play Store requires AAB files and secure release signing

**Do not submit either existing direct-download APK as the Play Store release.** The customer direct-download APK uses the existing testing key; the delivery direct-download APK was produced by the legacy generated Android build. They must not be silently treated as Play release/upload credentials.

Each app has a separate manual AAB workflow that **requires a real, privately backed-up upload keystore** and never falls back to debug signing:

- Customer: [Build Play Store customer AAB](https://github.com/Programmer-s-Picnic/easymandi/actions/workflows/playstore-customer-aab.yml)
- Delivery partner: [Build Play Store delivery partner AAB](https://github.com/Programmer-s-Picnic/delivery-app/actions/workflows/playstore-delivery-aab.yml)

The workflows run `flutter analyze`, `flutter test`, `flutter build appbundle --release`, ZIP integrity checks and JAR signature verification; successful releases produce downloadable AAB artifacts in GitHub Actions.

### Private GitHub Actions secrets — customer repository

Configure under `Programmer-s-Picnic/easymandi` → Settings → Secrets and variables → Actions:

| Secret | Value |
|---|---|
| `EASYMANDI_UPLOAD_KEYSTORE_BASE64` | Base64 contents of dedicated upload keystore |
| `EASYMANDI_UPLOAD_STORE_PASSWORD` | Keystore store password |
| `EASYMANDI_UPLOAD_KEY_ALIAS` | Upload signing key alias |
| `EASYMANDI_UPLOAD_KEY_PASSWORD` | Upload signing key password |

### Private GitHub Actions secrets — delivery repository

Configure under `Programmer-s-Picnic/delivery-app`:

| Secret | Value |
|---|---|
| `EASYMANDI_DELIVERY_UPLOAD_KEYSTORE_BASE64` | Base64 contents of delivery upload keystore |
| `EASYMANDI_DELIVERY_UPLOAD_STORE_PASSWORD` | Delivery keystore store password |
| `EASYMANDI_DELIVERY_UPLOAD_KEY_ALIAS` | Delivery upload key alias |
| `EASYMANDI_DELIVERY_UPLOAD_KEY_PASSWORD` | Delivery upload key password |

Keystore material must **never** be committed to GitHub. Back up the keystore and passwords offline in a secure location, since the same Play upload key should be used consistently for later updates (or rotated via Play Console's supported process). Do not share passwords in GitHub issues, chat messages or source files.

### Package IDs and initial versions

| App | Android application ID | Current tested app version |
|---|---|---|
| Easy Mandi customer | `in.easymandi.easy_mandi` | `1.3.11+22` |
| Easy Mandi Delivery Partner | `live.learnwithchampak.delivery_partner` | `1.3.2+12` |

These app IDs are generated by the existing Flutter CI workflows. The Play Store listing must use the same application ID, and newer submissions must always have a higher version code.

**Customer Google Sign-In:** Register the Play app-signing certificate SHA-1 and/or upload certificate SHA-1 in Google Cloud/Firebase as appropriate for your OAuth integration. The existing customer testing-key SHA-1 alone will not authorize Play-installed binaries.

**Before submitting to Google Play:**
1. Confirm who owns both developer-account listings and whether either package ID already exists on Play.
2. Prepare approved production privacy-policy URLs, account-deletion instructions if account creation is offered, Data safety responses, contact/support details, screenshots, descriptions, content rating and the appropriate Google Play testing track.
3. Review permissions actually used (customer: location, image picker and camera/QR as applicable; partner: camera scanning) and Play's current target API / app access requirements. Provide test credentials or reviewer instructions where needed.
4. Supply and back up dedicated upload signing key(s), add GitHub Secrets, then run each AAB workflow manually.
5. Download and upload the **AAB artifacts** to Play Console; independently confirm Play App Signing setup, closed/internal testing, review and rollout status.

The direct APK files at the three public URLs will remain available independently from Play Store packages. Changing signing certificates may require an uninstall before installing an APK signed under a different certificate; plan migration carefully.
